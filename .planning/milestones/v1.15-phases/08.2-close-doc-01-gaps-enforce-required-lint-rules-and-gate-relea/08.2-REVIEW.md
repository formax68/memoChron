## Info

### IN-01: Debug wrappers evaluate call-site arguments even when DEBUG is false

**File:** `src/services/CalendarService.ts:384`
**Issue:** Before this phase, `if (DEBUG) console.error(...)` skipped evaluating the arguments. Now `debugError(...)` always builds its arguments, and only then does the empty-bodied wrapper discard them. At `CalendarService.ts:384-388`, every non-200/403/404 response interpolates the whole `response.text` into a new string. That text can be a large HTML error page. `timezoneUtils.ts:217` also allocates an object literal on every conversion failure. The `debug.ts` header states this cost, so the behavior is intended. The cost is small but real, and esbuild does not remove calls to empty functions in other modules.
**Fix:** Accept it as documented. Alternatively, export the `DEBUG` const (or an `isDebug()` helper) and guard the expensive call sites (`if (DEBUG) debugError(...)`), or truncate the body (`response.text?.slice(0, 200)`).

### IN-02: `lint:directives` fails open when `grep` errors

**File:** `package.json:12`
**Issue:** The pipeline is `! grep ... src/ | grep -vE ...`. The pipeline's exit status comes only from the last `grep -v`. If the first `grep` fails (exit 2: missing `src/`, an unreadable file, a permission error), the second `grep` gets no input or partial input, exits 1, and the negation turns that into success. A probe with no `src/` directory exited 0. In the current gate `eslint src/` runs first and fails on a missing `src/`, so the realistic exposure is limited to unreadable individual files.
**Fix:** Make the first `grep` fail the script explicitly, for example with a small Node script `scripts/check-directives.mjs` that exits non-zero on read errors, or by capturing the `grep` status in `sh` before filtering.

### IN-03: The lint script uses POSIX-shell syntax and does not run on Windows shells

**File:** `package.json:10-12`
**Issue:** `lint:directives` depends on `!` pipeline negation, single-quoted regexes and `grep`. On Windows, npm runs scripts through `cmd.exe` by default, so `npm run lint` (which chains `lint:directives`) fails for Windows contributors. The release CI runs on `ubuntu-latest`, so the gate itself works.
**Fix:** Move the directive check into a cross-platform Node script (this also resolves IN-02), or document that the lint gate requires a POSIX shell (for example, `npm config set script-shell` to Git Bash).

### IN-04: The directive guard matches any prose use of the word "eslint" in `src/`

**File:** `package.json:12`
**Issue:** The first alternative `(^|[^-[:alnum:]_])eslint([^.[:alnum:]_]|$)` matches the bare word in any comment or string, for example `// see the eslint docs`. A probe confirmed that this fails the gate. The guard is fail-closed, so this is safe, but harmless comments or UI strings that mention ESLint will block a release with a message that does not explain why.
**Fix:** Accept it as intended conservatism and add a note to CONVENTIONS.md, or narrow the match to directive keywords (`eslint-disable`, `eslint-enable`, `eslint `, `eslint-env`) at comment starts.

### IN-05: TypeScript suppression comments are not covered by the guard

**File:** `package.json:12`
**Issue:** The obsidianmd preset sets `@typescript-eslint/ban-ts-comment` to `off`. The new directive guard checks only ESLint and `global`/`exported` directives. A `// @ts-ignore` or `// @ts-expect-error` can still silence type checking in `src/` without failing lint. None exist today. This is outside DOC-01's literal ESLint scope, but it is a related suppression channel that the gate does not close.
**Fix:** Optionally set `"@typescript-eslint/ban-ts-comment": ["error", { "ts-expect-error": "allow-with-description" }]` in `eslint.config.mjs`, or extend the directive guard to cover `@ts-` comments.
